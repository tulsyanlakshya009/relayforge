# Operations and troubleshooting

## Review a completed increment

A `done` result is the start of a review, especially during initial adoption. Check the
application diff, acceptance criteria, real test output and architecture changes together.
Reports containing test names are evidence supplied by the agent; independent check logs
show which configured commands the runner actually executed.

| Project file | Purpose and ownership |
|---|---|
| `REQUIREMENTS.md` | Human-approved numbered input; import explicitly |
| `REQUIREMENT_CHANGES.md` | Human-authored amendments; import explicitly |
| `MASTER_PROMPT.md` | Human-editable workflow instructions and report contract |
| `PLANNED_REQUIREMENTS.md` | Proposed scope generated by planning; review before importing |
| `SYSTEM_DESIGN.md` | Agent-maintained architecture, interfaces and decisions |
| `CHECKLIST.md` | Generated state for features, plans, changes, bugs and gates |
| `BUGS.md` | Generated defect checklist and requirement targets |
| `CURRENT.md` | Summaries and test evidence for all currently done non-gate items, including plans |
| `HISTORY.md` | Selected lifecycle events rendered with UTC timestamps and local version labels |
| `.relayforge/config.json` | Per-project runtime configuration |
| `.relayforge/state.sqlite3` | Queue, attempts, summaries, event log, pause and reset state |
| `.relayforge/runs/<attempt>/` | Prompt, agent log, agent report and independent test logs |

Generated Markdown is rebuilt from state and can overwrite manual edits to those files.
Write durable application guidance in an appropriate authored document and reference it
from requirements or the design file. Workflow version labels such as `v17` refer to event
sequence numbers; they are not Git tags, release versions or a semantic-versioning scheme.

## Find attempt evidence

Each execution creates a random attempt directory. Look for:

- `prompt.md`: the exact prompt supplied to the agent.
- `agent.log`: combined stdout and stderr from the agent process.
- `report.json`: the agent-authored result, if it was written.
- `test-0.log`, `test-1.log`, and so on: configured verification commands that ran.

A failed run may not have a report or test logs. Match the error in `HISTORY.md` to the
attempt directory; started events also store the attempt ID in SQLite. Use the directory's
modification time to locate recent attempts without directly editing database records.
Logs are not automatically rotated or redacted. Archive old attempts when appropriate,
and redact project content and credentials before sharing logs.

## Recover a failure

1. Inspect `status`, the application's diff and the latest attempt logs.
2. Fix the cause: authentication, permissions, dependencies, report formatting, or application behavior.
3. For an unfinished blocked item, use `retry ID`; ordinary failed items remain pending.
4. Run `tick` and review its result before restarting a continuous worker.

```bash
relayforge --project /absolute/path/to/my-app retry 1.2
relayforge --project /absolute/path/to/my-app tick
```

Do not mark checkboxes manually to bypass verification. Retrying a done item is rejected;
report a bug or import a new human change to revisit completed behavior.

## Common symptoms

| Symptom | Meaning / recovery |
|---|---|
| `Run relayforge init first` | The selected path has no RelayForge config; check `--project` before initializing |
| `Project already initialized` | Reuse the existing state and configuration; initialization is not a reset operation |
| `Another runner is active for this project` | A tick holds the lock; wait for it to finish or stop the foreground runner normally |
| `doctor` succeeds but the agent fails | Doctor does not check account login, tool approvals or actual provider compatibility; inspect `agent.log` |
| Repeated `waiting` | The persisted `resume_at` timestamp is in the future; no agent is launched during that cooldown |
| Unexpected `limited` | A heuristic log match may have classified a non-credit error as a limit; inspect the exact provider message |
| No checklist tick after successful process exit | A fresh valid report and independent checks are still required |
| `Report task/attempt mismatch` | The agent used an old or incorrect report ID; keep the prompt's exact values |
| Host verification command failed | Inspect its `test-N.log`; a repair is queued unless already repairing a bug |
| Gate reports defects | Repair them first; the gate cannot pass with reported bugs |
| Retry budget exhausted | The item is blocked; fix the cause and use `retry ID` |
| Agent modified human-owned inputs | Originals are restored after the normal attempt; review changes and report, then retry |
| Changing reset configuration still produces `waiting` | Configuration changes do not replace the existing persisted cooldown |
| Editing or deleting requirement lines does not update the queue | Imports add approved work; immutable titles require changes, and deletion is unsupported |

If a configuration error prevents even `configure` from running, stop the worker and repair
`.relayforge/config.json` manually using [the configuration defaults](configuration.md).
Avoid deleting `.relayforge` as a shortcut: that would discard history, queue and resume state.

## Stop, pause and restart

`pause` takes the same lock as execution. It fails while an attempt is active rather than
interrupting it. For a foreground worker, use Ctrl-C to stop the active process group, then
set pause before a scheduler starts another attempt. Disable the scheduler first when
needed to avoid a race.

Source edits survive interruption. On a later tick, a leftover `running` task is returned to
pending after the runner acquires the lock. The next attempt receives fresh context and
is instructed to inspect existing partial work. This is task resumption, not guaranteed
continuation of the provider's original conversation.

A forced process kill or machine crash can leave subprocesses running or interrupt input
restoration. Inspect active processes and application files before restarting after an
abnormal shutdown. Normal timeouts and Ctrl-C are handled; arbitrary crash recovery is
not fully guaranteed.

## Back up or move a project

Stop the worker and scheduler before copying the managed application and `.relayforge`
together. Include the entire state directory, not only the primary SQLite file; SQLite can
have accompanying WAL files. Copying a live database by ordinary file operations is not a
consistent backup method. Keep source and state from the same point in time.

On a new machine, reinstall RelayForge and the selected CLI, authenticate again, review
PATH and any absolute paths in configuration, and point `--project` at the copied project.
OpenClaw workspace configuration and provider sessions may need separate updates.
Git alone does not move local resume state because `.relayforge/` is ignored.

## Execution boundaries

Agents and verification commands execute with your local permissions and inherited
environment. Use trusted projects and the agent's native sandbox. Human inputs are
snapshotted and restored after normal attempts, but this is accidental-edit protection,
not isolation against a malicious process. The database and generated documents are
protected by instructions rather than a separate security boundary.

The master prompt asks agents not to publish, deploy or push. RelayForge itself performs
none of those actions, but it cannot guarantee a broadly permitted agent will obey every
instruction. Scope native tool permissions accordingly. There is no automatic code rollback,
automatic commit, universal spending cap or credential-management service.
